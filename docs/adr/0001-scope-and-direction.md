# 0001 产品范围与界面路线

- 日期：2026-10-20
- 状态：已接受

## 背景

骨架建立后，有四个会影响全局的方向需要先固定，否则后续每个技术选择都要重新讨论一遍。

## 决定

1. **首批用户：朋友小圈子，10–50 人。** 用房间码邀请，不做公开房间发现，几乎不需要内容治理。
2. **Android 分发：侧载 APK / 内测分发。** 不为了应用商店审核口径牺牲前台服务与 UsageStats 的采集能力。
3. **界面路线：双端原生（Windows WPF + Android Compose），共用 design tokens。** 不采用一套跨端 UI 框架。
4. **状态展示：显示应用名与类别。** 状态文本由用户可编排的「状态块」组成：可增删、拖拽排序、
   每个应用可配单独模板，Windows 端支持 PS1 自定义文本块。

## 补充：参考实现确认（2026-10-20）

看过参考产品的两张截图后，补充三点交互层面的决定：

- 房间内以**成员列表**呈现（头像 / 昵称 / 角色徽章 / 状态行 / 操作），不做卡片网格；
- 状态配置的界面形态是**同步列表**：块可拖拽排序，每块可设置、删除，底部快捷添加快捷项；
- 自定义文本块在 Windows 上支持 `$()` 调用命令，但表达式与路径只存本机，仅输出文本参与同步；
- **窗口标题默认不同步**，只有用户按应用显式开启、且实时预览确认后，才随该应用的块上报。

## 后果

- **房间模型可以极简**：房间码 + 成员列表即可；账号可先用匿名设备，后续再补绑定。
- **Android 权限策略以可用性优先**：首次启动要给出清晰的权限引导图文，不能依赖商店的标准化流程。
- **两套 UI 实现**：靠 tokens 与截图验收对齐；跨端共享的是契约与测试用例，不是组件代码。
- **状态块成为核心差异化功能**，需要独立规格与两端一致性测试，见 `shared/status-blocks/`。
- **需要重视脚本块的边界**：脚本只在本机执行，输出按不可信文本处理，长度与字符都要截断清洗。

## 什么情况下重新考虑

- 用户规模超出小圈子（> 500 人），需要公开发现与治理时，重新评估房间与账号模型；
- 端侧 UI 维护成本持续高于预期，或两端功能开始明显不同步时，重新评估 Compose Multiplatform；
- 应用商店成为主要分发渠道时，重新评估前台服务与 UsageStats 的合规方案。
