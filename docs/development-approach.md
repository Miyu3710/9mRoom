## 0. 一句话概括

9mRoom 的表面是一个自习室界面，实质是一套**跨设备的在场感系统**：
持续采集「此刻在做什么」，归一化成统一模型，实时同步给同房间的人。

## 1. 先把问题摆正

三件事要分开看：

- **产品问题**：一群人在一个房间里看见彼此在学习，产生轻量的同伴压力与陪伴感。
- **工程难点**：在两个差异极大的系统上稳定拿到「此刻在做什么」，并且不让人反感。
- **工程噪音**：界面统一、账号体系、部署运维——重要，但都是可控的常规工作。

**结论：风险和工期主要不在界面，而在两端的「状态采集」。**
所以先验证采集可行性，再谈框架；UI 统一退居第二位，用设计规范解决。

同时先定一条产品底色：这是**协作式自习，不是员工监控**。

- 默认不上传窗口标题、文件名、URL、屏幕内容；窗口标题需按应用显式开启，并实时预览
- 不做键盘记录、不做截图
- 状态是「自我报告 + 本机识别」的结合，允许随时暂停，且暂停不显示为偷懒

## 2. 功能拆成六条独立数据流

| 切片 | 用户看到什么 | 数据来源 | 能否先造假数据 |
| --- | --- | --- | --- |
| 在场 Presence | 在线 / 离开 / 离线、上次同步时间 | 心跳 | 能 |
| 活动 Activity | 正在用哪类应用、哪个应用 | 前台窗口 / UsageStats | 能（手动指定） |
| 音乐 Music | 歌名、歌手、播放进度 | SMTC / MediaSession | 能（假元数据） |
| 专注 Focus | 番茄剩余、今日专注时长 | 客户端计时 + 服务端会话 | 能 |
| 状态文本 Status | 那行由块拼成的展示文本 | 块配置 + 待办 + 开机时长 + 命令输出 | 能 |
| 房间 Rooms | 成员列表、角色、可见性 | 服务端 | 能 |

按这个顺序开发，每条都能独立演示；任意一条卡住，其余五条仍可上线。

## 3. 状态模型草案（v0，仅作为思考工具）

```jsonc
{
  "userId": "u_123",
  "roomId": "r_456",
  "device": "windows",              // windows | android
  "mode": "focusing",               // focusing | break | idle | away | invisible
  "activity": {                     // 结构化，供聚合与筛选
    "appId": "vscode",
    "category": "coding"
  },
  "music": {
    "title": "……",
    "artist": "……",
    "isPlaying": true,
    "positionMs": 42000,
    "durationMs": 288000,
    "sampledAt": 1730003580000
  },
  "focus": {
    "startedAt": 1730000000000,     // 服务端时间
    "plannedMinutes": 25
  },
  "status": {                       // 展示层，见第 4 节
    "layout": "inline",
    "separator": " | ",
    "blocks": [ /* … */ ]
  },
  "updatedAt": 1730003600000,
  "expiresAt": 1730003690000
}
```

四条规则：

1. **只保留最新值**，不做事件溯源。状态类数据的历史价值低，合并与存储成本高。
2. **`mode` 由客户端计算，服务端只做校验与兜底**；心跳断了，服务端把状态置为离线。
3. **时间只信服务端**。客户端上报「已专注 12 分钟」这类相对量，服务端换算成绝对时间；
   客户端本地计时使用单调时钟，避免系统时间被改动导致漂移。
4. **音乐只传文本与进度，不传封面**。远程用户没有你的音频文件，封面要么依赖第三方接口
   （版权与带宽问题），要么不显示——v1 选择不显示。

**为什么结构化字段和状态块同时存在**：字段用来算（统计几个人在写代码、筛选在看书的人），
块用来显示（每个人想怎么描述自己）。两者职责不同，允许有重叠。

## 4. 状态块与「同步列表」

参考实现只借鉴交互与信息密度，不复制配色与素材；公开仓库不包含参考截图。

### 4.1 它解决什么

固定的几个字段无法表达「我在被什么拷打」「整点薯条」。用户需要自己决定：

- 显示哪些块（应用、音乐、待办、计时器、开机时长、自定义文本）
- 什么顺序（拖拽）
- 每个应用用什么说法（`vscode` → 「搬砖中」，`chrome` → 「查资料」）
- Windows 上甚至可以用命令产出任意文本

### 4.2 关键决策：发结构，不发成品字符串

| 方案 | 问题 |
| --- | --- |
| 发送渲染好的整句话 | 无法本地走秒（每秒发网络消息），应用名无法按对方目录解析，服务端无法校验 |
| 发送结构化块 + 模板 | 接收端渲染，能走秒、能本地化、能逐块丢弃异常数据 |

唯一例外：命令块只上报输出文本，表达式本身永不出本机。

### 4.3 块类型（v1）

`app`（应用活动，含空闲状态）、`media`（歌曲识别，含进度外推）、`todo`（待办）、
`timer`（计时器，正计时/倒计时）、`uptime`（开机时长）、`text`（自定义文本）。

完整字段、占位符与 10 条渲染规则见 [`shared/status-blocks/`](../shared/status-blocks/README.md)。
两端实现必须通过同一份 [`fixtures.json`](../shared/status-blocks/fixtures.json)。

### 4.4 走秒与外推

`timer`、`uptime`、`media` 的进度都由接收端本地计算：

- 上报时带绝对起点或采样时刻，接收端每秒重算，**不产生额外网络流量**
- 渲染是纯函数 `render(blocks, now, catalog)`，因此天然可测

### 4.5 命令块

Windows 端自定义文本支持 PowerShell 表达式（`$()` 子表达式），例如开机时长脚本：

- 只在本机执行，表达式与脚本路径不上传
- 间隔 ≥ 30 秒，超时 3 秒，失败沿用上次结果
- 输出截断 80 字符、清洗控制字符
- 设置页必须提示：不要写密钥，输出会展示给房间成员

Android v1 只支持手动文本，不做命令求值。

### 4.6 编辑器形态

每块一行：拖拽手柄 → 图标与名称 → 一句说明 → 设置 / 删除；底部是快捷添加与自定义文本输入。
编辑时提供实时预览：「别人现在看到的是这样」。预览功能能挡掉大部分「我以为是私密的」误会。

## 5. 同步设计：两条通道

| 用途 | 通道 | 理由 |
| --- | --- | --- |
| 实时在场（谁在线、在做什么） | WebSocket 推送 | 变化频繁，只需要最新值 |
| 房间 / 成员 / 统计 / 账号 | HTTP | 需要可靠、可缓存、可重试 |

要点：

- **心跳 30–60 秒**，服务端 TTL 90 秒；客户端本地也判断「离开」
  （无输入 5 分钟、锁屏、屏幕关闭）。
- **状态块不单独开通道**，跟随 `presence.update` 一起发；变化做 1 秒合并窗口。
- **重连即全量**：断线重连后先收 `room.snapshot`，再恢复增量；**不做离线事件重放**。
- **幂等与乱序**：每条消息带 `id` 去重，带 `ts` 丢弃过期值。
- **指数退避**：1s → 2s → 4s …… 上限 60s 并加抖动，避免服务端重启时被同时打满。
- **容量估算**：100 人房间、每人 30 秒一条，入站约 3 条/秒，扇出约 300 条/秒。
  单个进程足够，不需要 Redis 或消息队列；等到需要多实例时再引入。
- **多端一致性**：同一账号在 PC 和手机同时在线时，presence 取「最近活跃设备」，
  UI 上标出设备图标——不要简单互踢。

## 6. 隐私：这是产品的一部分，不是合规章节

默认值决定产品气质。当前建议：

| 项 | 默认 | 可调 |
| --- | --- | --- |
| 应用信息 | 上报 `appId` + 类别 | 可降级为「只报类别」 |
| 窗口标题 | **默认不上报** | 黑名单模式：总开关开启后除黑名单外共享；单应用可隐藏 |
| 可见范围 | 房间内可见 | 仅自己 / 隐身 |
| 音乐 | 共享歌名、歌手与进度 | 可单独关闭 |
| 命令块 | 只上报输出文本 | Windows 独有，输出内容由用户负责 |
| 统计 | 只统计专注分钟数 | 可删除 |
| 保留期 | presence 不落库；会话统计 90 天 | 可配置 |

补充三点：

- **服务端不掌握进程名映射表**。映射发生在客户端，服务端只见 `appId`。
  即使数据库泄露，也无法还原出「谁在用哪个具体软件」。
- **隐身 ≠ 离线**。显式隐身要显示为「隐身」，否则会被误读为在摸鱼，用户就不敢用。
- **命令块是隐私上的新口子**：用户可以写 `$()` 读出任何东西并展示。
  产品能做的是提示与预览，不能替用户判断，所以「别人看到的样子」必须实时可见。

## 7. 平台能力地图

### Windows

| 需求 | 实现 | 坑 |
| --- | --- | --- |
| 前台应用 | `GetForegroundWindow` + `GetWindowThreadProcessId`；或 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 事件驱动 | UWP 窗口属于 `ApplicationFrameHost.exe`，要取子窗口的真实进程；管理员权限运行的程序可能读不到，降级为「受保护的应用」 |
| 空闲 | `GetLastInputInfo` | 全系统输入；锁屏与远程桌面下行为不同 |
| 音乐 | `Windows.Media.Control`：`GlobalSystemMediaTransportControlsSessionManager.RequestAsync()` | 需要 `net8.0-windows10.0.19041.0`；只对实现了 SMTC 的播放器有效 |
| 命令块 | PowerShell 表达式求值（`$()`） | 超时、输出截断、不得阻塞状态上报；脚本以当前用户权限运行 |
| 常驻 | 托盘 + 单实例 Mutex + 开机自启 | WPF 没有内置托盘图标 |
| 更新 | Velopack（候选） | 未签名安装包会触发 SmartScreen 提示 |

### Android

| 需求 | 实现 | 坑 |
| --- | --- | --- |
| 前台应用 | `UsageStatsManager.queryEvents` / `queryUsageStats` + `PACKAGE_USAGE_STATS` | 用户必须去系统设置手动授权；国产 ROM 会杀后台；轮询间隔要省电（30–60 秒） |
| 音乐 | `MediaSessionManager.getActiveSessions()` + 通知使用权 | 需要 `BIND_NOTIFICATION_LISTENER_SERVICE` 并在设置中启用；部分应用不暴露 MediaSession |
| 常驻 | 前台服务 + 常驻通知 | Android 14 起要求声明 foreground service type |
| 应用名 | `PackageManager` | Android 11+ 包可见性受限，用内置目录覆盖常见应用，未知归「其他」 |
| 省电 | 引导关闭电池优化、开启自启动 | 各家 ROM 路径不同，只能给图文引导 |

```
Windows: 前台窗口事件 ─┐
          SMTC 媒体会话 ─┼─→ 本地归一化(appId + 类别) ─→ 状态块合成 ─→ WebSocket
          空闲检测 ─────┤
          PowerShell ───┘

Android: UsageStats ────┐
          MediaSession ──┼─→ 同上（前台服务内完成，不做命令块）
          锁屏 / 无操作 ─┘
```

## 8. 技术选型：先别急，但要有倾向

原则：**哪边的原生能力最难做，就先保哪边。**
这个项目最难的是 Windows 的 SMTC、命令块，与 Android 的后台采集，不是界面。

| 组合 | Windows | Android | 服务端 | 优点 | 代价 |
| --- | --- | --- | --- | --- | --- |
| **A（推荐）** | .NET 8 + WPF | Kotlin + Compose | ASP.NET Core | 两端都用最成熟的系统 API；可复用既有 WPF/SMTC 与 Compose 经验；服务端与 Windows 同语言可共享 DTO | UI 写两遍；状态块渲染写两遍 |
| B | Compose Multiplatform (JVM) | 同左 | Ktor | 一套 UI 代码 | 要从 JVM 调 WinRT 拿 SMTC，托盘/自启/打包全要桥接——正好压在最难的地方 |
| C | Flutter | Flutter | 任意 | 一套 UI | 两套既有技术积累作废；Windows 侧插件生态弱，采集仍要写原生插件 |

服务端在 **ASP.NET Core** 与 **Ktor** 之间选，看哪边更愿意长期维护。
若选 ASP.NET Core，本机需要补装 .NET SDK（当前只有运行时）。

**“统一 UI”不等于“同一个 UI 框架”。** 组合 A 的代价是两份 UI 与两份状态块渲染，
但后者可以用同一份 `fixtures.json` 把漂移风险压到很低；组合 B 的代价则集中在最难的原生集成上。

## 9. 统一视觉怎么落到工程

1. `design/tokens.json` 作为唯一来源：颜色、字阶、间距、圆角、动效。
2. 生成 `Tokens.xaml`（WPF）与 `Theme.kt`（Compose）；生成物不入库，但生成脚本要能 diff。
3. 定义 12 个基础组件的对照表：按钮、图标按钮、输入框、卡片、头像、状态点、
   标签、分段控件、列表项、对话框、Toast、空状态。
4. 三张参考屏（成员列表 / 同步列表 / 设置）双端截图并排验收：
   允许 1–2px 差异，不允许布局结构差异。
5. 深色模式第一天就有，两端共用同一套语义色。

参考实现给出的尺度（约）：头像 40px、昵称 15px 加粗、状态行 13px 灰色、
行高 72px、卡片圆角 10px、状态行内用「 | 」分隔、每块一个 emoji 前缀。

emoji 在两端字形不同，只做点缀，不承载唯一语义——否则会出现「Windows 上是一坨方块」的问题。

## 10. 界面信息架构（v1 最小集）

      ├─ 成员详情     抽屉：今日时长、设备、最近活动类别

## 11. 里程碑：垂直切片

每个阶段的验收标准是「能演示」，不是「代码写完」。

| 阶段 | 目标 | 演示标准 |
| --- | --- | --- |
| M0 骨架 | server + WebSocket + 网页调试台；两端上报假状态与假块 | 浏览器里看到两个假用户的状态实时变化 |
| M1 Windows 采集 | 真实前台应用 → `appId` / 类别 | 切换应用，房间里 3 秒内变化 |
| M2 Android 采集 | Usage Access + 前台服务 | 手机锁屏 / 切换应用能被正确识别 |
| M3 房间 UI | 大厅 + 成员列表 + tokens 落地（状态行先用固定格式） | 双端并排截图不违和 |
| M4 音乐 | SMTC → MediaSession，接入 `media` 块 | 换歌 / 暂停能同步到房间 |
| M5 同步列表 | 块编辑器（拖拽、模板、每应用规则）、接收端渲染、计时器、自定义文本与命令、fixtures 单测 | 两个人看到彼此不同的组合文本，开机时长自己走秒 |
| M6 账号与持久化 | 登录、设备、会话、今日时长 | 重启客户端与服务端后数据还在 |
| M7 打磨与上线 | 断线重连、省电、自启、安装包、compose 部署 | 外网可用，连续跑一周不崩 |

**M0 的网页调试台是被低估的杠杆。** 不写客户端就能验收协议、复现并发问题、
给不写代码的人演示。用最朴素的 HTML + JS 即可，不要引入前端框架。

## 12. 先做三个 spike（各 1–2 天）

| # | 问题 | 做法 | 验收 | 失败退路 |
| --- | --- | --- | --- | --- |
| S1 | Android 能否稳定拿到前台应用 | 3 台不同品牌手机跑 8 小时，记录漏报与误报 | 前台切换 5 秒内识别，后台存活 ≥ 8 小时 | 降级为手动状态 + 粗粒度类别 |
| S2 | Windows SMTC 覆盖多少播放器 | 本机常见播放器逐一试切歌 / 暂停 / 进度 | ≥ 5 个主流播放器可读 | 显示「未在播放音乐」，不做标题猜测 |
| S3 | 状态同步语义是否够用 | WebSocket + 调试台 + 100 个虚拟客户端 | 断网 / 重连 / 断电后状态一致 | 退回 HTTP 轮询（15 秒），先保正确性 |

命令块不单独做 spike，放在 M5 内部用 1 天验证超时与输出清洗。

Spike 的结论写进 ADR，不要只留在代码注释里。

## 13. 风险清单

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Android 后台被杀 | 状态常年离线 | 前台服务 + 白名单引导 + 服务端 TTL + UI 显示「上次同步 3 分钟前」 |
| SMTC 覆盖不全 | 音乐状态缺失 | 优雅降级，不猜标题 |
| 两端状态块渲染漂移 | 同一份配置显示不一样 | 共用 `fixtures.json` 做单测；新增块类型必须同时补用例 |
| 命令块泄露敏感信息 | 用户把密钥打进命令 | 输入时提示、实时预览、输出长度限制；不替用户兜底 |
| 用户对隐私反感 | 不安装或直接卸载 | 默认最小上报；标题默认关闭；一键隐身 |
| 双端 UI 漂移 | 视觉不统一 | tokens + 截图验收 |
| 单人维护三套构建 | 迭代变慢 | 统一 `build.ps1` 习惯；CI 后置 |
| 工具链缺失 | 起步摩擦 | 补装 Git 与 .NET SDK；Docker 不必装在本机，构建放 Linux 或 CI |
| 服务端单点 | 宕机即全员不可用 | compose + 每日备份 + 健康检查 + 简单告警 |

## 14. v1 明确不做（写下来防止跑偏）

- 语音房、文字聊天、弹幕
- 「一起听」、同步播放
- 好友关系链、私信（成员列表里的「加好友」按钮先不做）
- iOS / macOS / Web 客户端
- 微服务、Redis、K8s、消息队列
- 应用使用时长的明细记录（只做专注时长汇总）
- 富文本 / Markdown / 图片状态块
- 封面与歌词同步
- Android 上的命令块
